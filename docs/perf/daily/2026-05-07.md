### [🟡] Over-eager Persistence of Canvas View
- **Symptom**: If the user pans or zooms around the canvas a lot, it may cause minor stuttering on weaker devices over time due to disk I/O, even though the visual changes are instant.
- **Location**: `src/core/store/index.ts:253`
- **Root cause**: The `canvasView` (which stores the pan/zoom camera coordinates) is included in the `partialize` whitelist of the main Zustand store. This means every time the camera moves, it tries to save those coordinates to the IndexedDB database. Even with debouncing, this is an anti-pattern that causes unnecessary I/O bottlenecks because pan/zoom is highly dynamic.
- **Suggested fix**: Remove `canvasView` from the `partialize` whitelist in `src/core/store/index.ts`. If persistence of camera position is desired, handle it separately upon exiting the app rather than live-syncing it.
- **Expected gain**: Completely eliminates background IndexedDB writes during canvas navigation, keeping the main thread and browser storage APIs free.
- **Fix risk**: Medium (might affect how the game loads if it relies on restoring the exact previous camera position).

### [🟢] O(N) Array Iteration on Existing Reference
- **Symptom**: The main game scene might run slightly slower than necessary when checking for active magical books (grimoires).
- **Location**: `src/app/components/ui/shell/SceneManager.tsx:64`
- **Root cause**: The `SceneManager` uses `useShallow` to select `activeGrimoires` from the game store. Because `activeGrimoires` is an existing array reference (not a dynamically created array or object), `useShallow` forces an element-by-element equality check (O(N)) instead of a simple direct reference check (O(1)). This slows down rendering checks unnecessarily.
- **Suggested fix**: Remove `useShallow` and just use `useGameStore(s => s.activeGrimoires)`.
- **Expected gain**: Faster state subscription checks in the core render loop by changing an O(N) check into an O(1) check.
- **Fix risk**: Low (safe to auto-fix).
