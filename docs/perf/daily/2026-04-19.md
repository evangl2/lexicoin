## Issues

### [🟡] B-001: No bundle chunking — all deps ship in one JS file

- **Symptom**: The app's loading spinner ("Initializing Lexicoin...") takes longer than it should on first visit, because the browser must fully download, parse, and execute the entire JavaScript bundle before anything can appear. On a typical mobile connection (~5 Mbps) a 600 KB+ gzipped bundle costs ~1 second of parse time alone.
- **Location**: [`vite.config.ts`](../../vite.config.ts) — no `build` section exists at all
- **Root cause**: Vite by default bundles everything into as few chunks as possible. Without `build.rollupOptions.output.manualChunks`, all of these end up in the same file: React, Framer Motion (`motion`), Supabase, Dexie, react-dnd, sucrase, and all app code. Large libraries that change rarely should live in their own cached chunk so the browser only re-downloads app code when you push a fix.
- **Suggested fix**:

```ts
// vite.config.ts — add a build section
build: {
    rollupOptions: {
        output: {
            manualChunks: {
                // These never change between deploys — users cache them forever
                'vendor-react':    ['react', 'react-dom'],
                'vendor-motion':   ['motion'],
                'vendor-supabase': ['@supabase/supabase-js'],
                'vendor-dexie':    ['dexie'],
                'vendor-dnd':      ['react-dnd', 'react-dnd-html5-backend'],
                'vendor-sucrase':  ['sucrase'],
            },
        },
    },
},
```

- **Expected gain**: Users who visited yesterday won't re-download `vendor-react` or `vendor-motion` after a code-only push. Estimated: saves 200–400 KB of re-download per deploy for returning users. Also makes each chunk smaller so parse time is distributed.
- **Fix risk**: Low — build-only config, zero runtime behaviour change. Easy to revert.

### [🟡] B-002: CJK fonts are local TTF files (65 MB total on disk)

- **Symptom**: First time a Chinese or Japanese character appears on screen, the browser queues a download for the matching font file. `NotoSerifSC-VariableFont.ttf` alone is **25 MB**. Even on a fast connection, a 25 MB TTF takes 2–5 seconds to transfer. During that window, CJK text renders in a system fallback font (jarring flash), then reflows when the file arrives.
- **Location**: [`src/assets/fonts/fonts.css`](../../src/assets/fonts/fonts.css) + `src/assets/fonts/`
- **Root cause**: The four CJK Noto fonts are self-hosted full variable TTF files. Variable fonts for CJK script cover the full Unicode CJK block (~20,000 glyphs), making the file enormous. The comment in `index.html` says *"CJK Fonts use System Fonts"* — but `fonts.css` actually registers them as local files via `@font-face`, so that comment is wrong.

  File sizes on disk:
  | Font | Size |
  |------|------|
  | NotoSerifSC | 25.0 MB |
  | NotoSansSC  | 17.7 MB |
  | NotoSerifJP | 12.9 MB |
  | NotoSansJP  |  9.1 MB |
  | **Total CJK** | **64.7 MB** |

- **Suggested fix** (two options, pick one):

  **Option A — Google Fonts CDN + unicode-range subsetting (recommended)**:
  Remove all four `@font-face` CJK blocks from `fonts.css` and delete the four TTF files. Replace with Google Fonts `<link>` in `index.html` using `&subset=chinese-simplified,japanese` (or `&display=swap`). Google Fonts serves pre-subsetted WOFF2 slices (~50 KB each), loading only the glyphs actually on screen. Total network cost drops from 65 MB to ~200 KB for a typical page.

  **Option B — Keep self-hosted but convert to WOFF2 + unicode-range slices**:
  Use `fonttools` / `pyftsubset` to generate unicode-range WOFF2 slices (the same technique Google uses). This is a one-time offline process. WOFF2 compression alone saves ~30–40% vs TTF (~45 MB → ~28 MB), and slicing means the browser only downloads the byte range it needs. Still much larger than Option A.

- **Expected gain**: Option A: CJK font cost drops from 65 MB → ~200 KB per language. Option B: drops to ~28 MB with lazy slice loading.
- **Fix risk**: Medium — removing self-hosted fonts changes what happens offline (no internet = no CJK fonts). Option A requires internet. Confirm whether the app needs offline CJK support before choosing.

### [🟢] B-003: LibraryInterface eagerly bundled into the main chunk

- **Symptom**: Every user downloads the Library view's code on first load, even if they never visit the Library tab. If `LibraryInterface.tsx` is large (it imports `lucide-react` icons, Supabase hooks, complex layout), that's wasted parse time on startup.
- **Location**: [`src/app/App.tsx:36`](../../src/app/App.tsx#L36) — `import { LibraryInterface } from "@/app/components/ui/visual/LibraryInterface"` is static (eager)
- **Root cause**: The view switch is `viewMode === 'LIBRARY'` — the component is only shown on demand, but the import is static so the code always loads eagerly. React provides `React.lazy()` specifically for this pattern.
- **Suggested fix**:

```tsx
// Replace the static import with:
const LibraryInterface = React.lazy(() =>
    import('@/app/components/ui/visual/LibraryInterface').then(m => ({ default: m.LibraryInterface }))
);

// Wrap the usage in a Suspense boundary:
viewMode === 'LIBRARY' ? (
    <Suspense fallback={<div className="flex items-center justify-center h-screen text-zinc-400">Loading library…</div>}>
        <LibraryInterface key="library" />
    </Suspense>
) : null
```

- **Expected gain**: Library code ships in a separate chunk, only downloaded when the user first opens the Library tab. Estimated savings from the initial bundle: depends on LibraryInterface's import weight, but likely 30–80 KB.
- **Fix risk**: Medium — requires adding a `Suspense` boundary and testing that the Library still loads correctly after the first click. Low chance of regression but needs manual verification.

### [🟢] B-004: No font preload hints — critical fonts discovered late

- **Symptom**: On page load, the browser finds out about `Cinzel-VariableFont.ttf` only after it parses the CSS file (which itself loads after the HTML loads). This causes a brief "flash" where card titles appear in Times New Roman (the system serif fallback) before snapping to Cinzel. The delay is typically 100–300ms even on fast connections.
- **Location**: [`index.html`](../../index.html) — no `<link rel="preload">` tags for fonts
- **Root cause**: Fonts declared in CSS are "late-discovered" resources — the browser doesn't know it needs them until it parses the stylesheet. `<link rel="preload" as="font">` tells the browser to fetch the font in parallel with the HTML, eliminating the delay.

  The challenge with Vite: production builds hash filenames (e.g., `Cinzel-VariableFont.abc123.ttf`), so static preload tags in `index.html` break in production. The correct Vite-compatible solution is a plugin.

- **Suggested fix**:

  Install and configure [`vite-plugin-preload`](https://github.com/sombreroron/vite-plugin-preload) or write a small Vite plugin that injects preload hints for the fonts after the build:

  ```ts
  // vite.config.ts — example using vite-plugin-preload
  import preload from 'vite-plugin-preload';
  plugins: [
      react(),
      tailwindcss(),
      preload({ rel: 'preload', include: /Cinzel.*\.(?:ttf|woff2)$/ }),
  ],
  ```

  Alternatively, convert fonts to WOFF2 and embed them as base64 in the CSS for the two smallest fonts (Cinzel is only 126 KB — a reasonable inline candidate).

- **Expected gain**: Eliminates FOUT (flash of unstyled text) for card titles. Users see the correct font from first paint.
- **Fix risk**: Low if using a plugin; Medium if doing the base64 embed (increases CSS size by ~170 KB for Cinzel).

Lower priority — fix B-001 first.
- **Fix risk**: Low for B-001 workaround; Medium for the async refactor.
