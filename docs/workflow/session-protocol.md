# AI 会话协议(开局 / 收尾清单)

> 状态: 现行 · 类型: 流程 · 更新: 2026-07-03
> 📖 人话: 每次 AI 干活的固定开场和收场动作。文档不烂尾全靠收尾清单,这是上一套审计制失败后的替代方案。

## 开局(动手写代码之前)

1. 读 `CLAUDE.md`(自动加载)→ [docs/INDEX.md](../INDEX.md) → 按任务路由表读相关文档
2. 涉及 Pixi 重构:核对 [roadmap.md](../refactor-pixi/roadmap.md) 当前 Stage,不要跳阶段
3. 想推翻任何现行做法之前:先读 [decisions/](../decisions/) 里相关 ADR。**不得擅自推翻 ADR**,有异议向作者提出
4. 读到与代码不符的文档:当场修正或标记归档(规范 §3.3),不要带着错误认知继续干活

## 收尾(commit 之前,逐条核对)

| # | 检查 | 动作 |
|---|---|---|
| 1 | 本次改动是否改变了模块结构、数据流、约定? | 更新对应架构/指南文档 |
| 2 | 本次是否做出了新的选型/禁令/方向性决策? | 写新 ADR 并登记 INDEX |
| 3 | 是否推进/完成了 roadmap 的 Stage? | 更新 roadmap 状态标记 |
| 4 | 是否新建了文档? | 补文档头 + 登记 INDEX |
| 5 | 是否发现了值得记录的坑? | 追加到对应排错/指南文档(不新开文件) |
| 6 | 文档改动与代码改动**同一个 commit** | — |

## 会话中的文档纪律

- 新知识优先**追加到现有文档**,开新文件是最后手段(文件越多越不透明)
- 一次性的分析/计划类产出(方案对比、调查报告)不进 `docs/`,留在对话里;只有沉淀为"现行事实/决策/规则"的内容才落盘
- 修改 GDD 属于设计决策,必须经作者确认,AI 不得代改
